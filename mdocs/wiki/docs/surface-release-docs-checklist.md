When a new surface ships (kimi-code in 2.0.0 was the case that exposed this), these doc spots reliably drift — audit all of them before considering a release documented:

1. **README.md** — capability table row, Entry Points bullet, Architecture tree (src/surfaces/ listing), per-surface Usage section, every surface enumeration ("hosts that load plugins", "tool-bearing surfaces", workflow-enforcement sentence), and any version-pin examples (stale pins like `harness-mdocs@0.4.0` survive for releases).
2. **docs/user-manual.md** — a new numbered install section in §2 per surface; renumber carefully.
3. **docs/agent-manual.md** — header scope line, §1 tool-bearing-surface parenthetical, §5 subagent-dispatch native/manual split, §8 per-surface table row + notes, §11 SessionStart/orientation bullets.
4. **docs/packaging-strategy.md** — entrypoint bullet, stamp-versions manifest list, CI Node matrix, dry-run tarball checklist (must match package.json `files`), per-surface dogfood section.
5. **Generated mirrors** — `agents/mdocs-orchestrator.md` is GENERATED from `src/generation/fragments/opencode-agent-orchestrator.md`. Never hand-edit it: edit the fragment and run `npm run generate:agents`. Hand-edits fail `check:agents` (`byteDrifted`) inside `npm run quality`.
6. **Build scripts** — `scripts/stamp-versions.js` must include the new surface's plugin manifest or `check:versions` fails.

The canonical tool set every tool-bearing surface registers is enforced by `tests/surfaces/parity.test.ts` (`CANONICAL_TOOL_NAMES`) — any per-surface tool list in docs must match those 13 names exactly.
