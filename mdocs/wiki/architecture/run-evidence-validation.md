## Purpose
WP-220 validates action receipts and execution reports as bounded evidence claims. Validation is pure: no effects, persistence, budget settlement, controller transition, report acceptance, or authority grant.

## Model
- `src/agents/run/evidence/` defines strict evidence envelopes, operation-specific redacted metadata, deterministic workspace fingerprints, and receipt/report validators.
- Every result is detached, deeply frozen, and carries `authority: false`. `valid` means internally consistent evidence only; WP-230 controller logic still owns acceptance and state transitions.
- Receipt projections retain strict sealed redacted envelopes. Reports verify projections transitively rather than trusting mutable summaries.
- Validation contexts bind run/project, approved plan and graph, revision/epoch/cancellation generation, controller-root or delegation-ticket lineage, ticket budget reservation, lease kind/ref/generation/fence/window, expected report destination/schema, protected intent timestamps, and trusted usage reconciliation.

## Redaction and fingerprints
- Metadata uses static operation-specific allowlists. Unknown or sensitive keys reject the whole claim; values are never best-effort masked. Raw content, stdout/stderr, request/response bodies, headers, cookies, credentials, environment values, secrets, and tokens are forbidden.
- Workspace fingerprints commit version, explicit write-selector scope, sorted canonical project-relative entries, file digests, symlink targets, kinds, and sizes. Hostile input has depth/node/string/key/aggregate-byte bounds.
- Paths reject escape, wildcard, separator, control, Unicode-normalization, Windows device/alias, and portable case-fold collisions.
- Report causality validates every observed path against parent before/after snapshots. Serial same-path effects must chain; concurrent overlap rejects; disjoint parallel work, narrower child scopes, no-op effects, and write-then-restore remain representable.

## Lineage and closure
- Supported authority forms are nondelegating `controller-root`, `PLAN_ROOT -> EXECUTION`, and `EXECUTION -> LEAF`; no root-to-leaf or recursive EO path exists.
- LEAF evidence binds its parent EO workstream lease; sibling leaves may share that exact lease tuple.
- Each child has one exact trusted ticket/report/digest/lease/budget tuple and exactly one successful mediated `agent.spawn` receipt whose child ticket and agent/node target match.
- Receipts, actions, idempotency identities, child reports, criteria, artifacts, evidence records, disclosures, and transitive owners close exactly. Orphan, duplicate, relabeled, resealed, stale, or foreign evidence fails.
- Receipt/report replay is byte-identical only. Lower generations quarantine as stale; impossible future generations reject.

## Usage and budgets
- WP-210 and WP-220 share canonical usage-sample schema, digest, and exact reservation accounting.
- Authoritative token/cost/action samples derive actual usage; zero overshoot, currency, telemetry, descendant accounting, ticket-to-reservation bijection, and sample digest are enforced.
- Repeated receipts for one ticket reservation deduplicate exact snapshots. Cross-ticket reservation reuse rejects. Pending usage blocks completion; unresolved usage quarantines; released usage is allowed only for corroborated no-effect failure.
- Report reservation snapshots remain exact; explicit subtree totals aggregate each unique reservation once.

## Quarantine boundary
Structurally valid late evidence with stale/revoked/expired/unresolved ticket, lease, graph epoch, cancellation generation, or usage authority is quarantined. Malformed, sensitive, tampered, impossible-future, lineage-breaking, budget-invalid, or open-reference claims are rejected.
